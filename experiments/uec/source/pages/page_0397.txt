3.5.16.8 PCM Telegram 
The PCM Telegram control packet, Telegram CP, is defined to support extensible, typed control-plane 
messaging between UET endpoints implementing PCM. The Telegram CP provides a generic container 
for small, structured control messages (aka telegrams) whose semantics are identified by a type 
identifier and whose payload format is defined by the corresponding telegram type. 
The Telegram CP is identified by a unique control packet type value (see Table 3-82). Packets are 
allocated a unique PSN. Packets MAY be sent in either direction on an established PDC. The pds.flags.ar 
bit MUST be set to 1. 
The Telegram CP payload is carried in the payload field and has a fixed size of 32 bytes (see Section 
3.6.18.6.3). This payload is submitted to the PCM subsystem for further processing. If the destination 
PDC is not controlled by PCM, the receiver returns a UET_UNEXP_EVENT NACK in accordance with the 
PDS NACK generation behavior described in Section 3.5.12.7. 
3.5.16.9 CP Summary Table 
Table 3-82 summarizes the fields used in CP headers by type. Source to destination means transmission 
from the initiator to the target on the forward direction, and from the target to the initiator on the 
return direction. 
RODL MUST support the Close Command CP and Close Request CP. RODL does not require generating 
other control packets. Implementations MUST accept and respond to NOOP, ACK Request, Clear, and 
Clear Request CP messages. Support for Probe, Credit, Credit Request, and Negotiation CPs are not 
required on RODL, and these packets may be dropped without response.
