Algorithms send telegrams locally or to remote peers as follows: The algorithm sets the telegram type 
using the uet_set_tgm_type() function, populates the field values using the appropriate 
uet_set_field_*() functions, and transmits the message locally or to the remote peer using the 
appropriate function. Algorithms can transmit telegrams regardless of the callback invocation context. 
Implementations MUST support sending local telegrams and they MAY support sending telegrams to 
remote peers or collector nodes. 
Telegram structures are invalidated when the current invocation exits; algorithms MUST reconstruct the 
structure on subsequent invocations as required.

3.6.18.6.3.1 Processing Telegrams 
The PCM runtime is responsible for forwarding sent telegrams to the local host or remote peer as 
follows: 
Local telegrams are forwarded to the host in an implementation-specific manner. The mechanism used 
to receive logs and alert host software is configuration-specific. Example mechanisms include: 
• Kernel logs (e.g., dmesg). 
• Device-specific control APIs (e.g., netlink/sysfs/debugfs). 
• Vendor-specific user-space daemons. 
Peer telegrams are forwarded to the remote PDC via Telegram CPs (see Section 3.5.16.8). Telegram 
structures are encoded as payload in these control packets with the following format: 
• Fixed header (2 bytes): 
o type_id (8 bits): Identifies the telegram type and determines the interpretation of the 
payload. This field MUST be populated with the telegram type identifier as defined by the 
corresponding telegram YAML specification. 
o reserved (8 bits): Reserved for future use. This field MUST be set to 0x0 by the sender and 
MUST be ignored by the receiver.
