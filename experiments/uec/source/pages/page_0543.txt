3.6.18.7.4 Reset and reinitialization 
Recovery from the ERROR state is outside the scope of PCM. An implementation MAY provide a 
platform-specific mechanism (e.g., driver, firmware, or device reset) to reinitialize a CCC. If a CCC is 
reinitialized, the implementation MUST ensure the reinitialized CCC appears as a fresh instance with no 
retained PCM state. 
3.6.18.8 Algorithm Lifecycle Management 
Logically, PCM algorithms are loaded, instantiated, configured, assigned to a subset of data traffic, and 
activated to provide congestion control capabilities. The remainder of this section outlines this flow. 
3.6.18.8.1 Loading Algorithms 
PCM algorithms are dynamically loaded using implementation-specific tools. Algorithm implementors 
specify required PCM features for a particular algorithm by providing a load-time specification along 
with the algorithm that is consumed by the load tool to determine if the implementation can support 
the algorithm and to configure the PCM subsystem for the algorithm. Load-time specifications provide 
the following information on an algorithm basis: 
1. The set of configuration parameters and associated default values. 
2. All signals and their mapping to indices, and initial values for new CCCs. 
3. All outputs and their mapping to indices. 
4. All local storage variables and their initial values. 
5. The invocation callback function. 
6. The set of initial triggers for new CCCs. 
7. The default cwnd and send_rate values for new CCCs. 
Load-time specifications are expressed in a hierarchical YAML format as described in Section 3.6.18.8.5. 
3.6.18.8.2 Algorithm Instances 
Algorithm instances are specific, independent realizations of a loaded PCM algorithm, complete with 
configuration and state, and are used to manage congestion control for an administrator-defined subset 
of bulk data generated by the FEP.
