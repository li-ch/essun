The submission door

Community operating points, checked for fairness

Anyone can submit an operating point — a workload, the shared free-parameter record, one or two arms over committed topology files, and results that cite content-addressed run ids. The door is a documented format and a validator, not an institution: malformed input is rejected by design, fairness is checked delta-zero-style (everything shared must be verified equal; only the declared axis may differ), and every number must trace to a run id exactly. Reviewed submissions are listed below — published and rejected alike, nothing filtered.

What the door checks

Fairness, delta-zero-style

The same bar the cross-fabric matrix holds itself to ("What a fair comparison requires"), enforced by a validator instead of by prose:

Identical open choices

One shared free-parameter record feeds every arm. The validator reads each arm's committed topology file and checks every declared-shared parameter is carried there with the declared value — equal inputs verified from the files, not from the submission's prose.

One axis, named

The arms may differ only on the axes the submission declares — the validator recomputes the actual difference set and requires exact equality with the declaration. An undeclared difference is a smuggled asymmetry; a declared axis that does not differ is a mislabeled comparison.

Run id or it didn't happen

Every result cites content-addressed run ids, and the review step re-executes them from the committed manifests: a submitted value that does not match the stored observation exactly is refused. No number enters the table on prose.

The delta-zero control

A submission may declare its arms a control pair — claimed numerically identical. Then every paired observable must be exactly equal, and the claim is checkable by anyone re-running the two manifests.

How to submit

Format, validate, post

  1. Read the format spec (docs/submission-format.md) and copy the example (examples/submission.example.yaml).
  2. Run your operating point from committed inputs (make run EXP=<manifest>) and note the printed run ids.
  3. Validate locally: make check-submission FILE=your-submission.yaml (add VERIFY=1 to also check the store gates). The door refuses malformed input by design — the error names the field.
  4. Post it with the comparison-submission issue template. A maintainer re-executes the cited runs, appends the review, and the record renders here.

New topology files or workloads enter through pull request (license review precedes ingestion of any standard document); the door only accepts operating points re-runnable from the public tree.
