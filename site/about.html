What a good pull request looks like

Contributing

Set up with make bootstrap (creates .venv and installs the package with dev extras), then make test; make ci-local runs the exact CI sequence locally. The full guide, with the machinery behind each rule, is CONTRIBUTING.md in the repository.

A good pull request:

  • Tests pin the change. Golden tests write expected values by hand — a closed-form identity, a conservation law — never pasted back from the implementation's output, and schema or contract changes ship negative tests alongside golden ones. Determinism is required throughout: no unseeded randomness, integer byte counts, fixed tie-breaking; a rerun of the same manifest must reproduce the same content-addressed run id, and a comparison across different workloads is not a controlled ablation.
  • A run id for anything numeric. Behavioral claims cite a run id plus the manifest and commit that reproduce it — "a claim without an id is an opinion." Interface-affecting decisions ship with a short decision record in the pull request.
  • An evidence label in the commit title. The lowest honest rung of PROPOSED / IMPLEMENTED_UNVERIFIED / VERIFIED / CALIBRATED / EXTERNALLY_REPRODUCED; a citing party cannot upgrade a label it reproduces.

Issue and pull-request templates encode the same discipline: the bug-report template (it asks for the run id, manifest, and commit) and the pull-request template.

Getting help

Support

  • Bugs and capability gaps: GitHub issues — the bug-report template asks for the run id, manifest, and commit, because a report with those three is reproducible.
  • Usage questions: start from the Quickstart page and docs/usage.md in the repository (two worked examples with real outputs).
  • Everything else: open an issue; there is no chat channel or mailing list today.

Standing on pinned, recorded work

Acknowledgments

essun stands on pinned, recorded upstream work — each ingested only after license review, pinned by commit with recorded digests, and credited with its exact contribution:

  • ASTRA-sim (MIT; Georgia Institute of Technology, Facebook Inc) — pinned at 4ce9ecf; its analytical frontend is the project's discrete-event second backend in Docker.
  • uet-htsim (BSD-2-Clause; Ultra Ethernet Consortium Transport-WG) — pinned at 65ea315b; adapted as the third backend uet_htsim_cms.
  • csg-htsim (BSD-2-Clause) — built and runbooked, with its run-to-run nondeterminism root-caused and an env-seeded patch recorded; the essun adapter is future work.

The calibration anchors cite public measurements from the GPU-fabric and collective-communication literature (23 anchors staged with sources in docs/calibration/) — cited as measurements with their contexts, never laundered into model constants. The htsim lineage itself (the open-source network simulator tradition) underlies two of the three pinned simulators.

How this site is built

Site colophon

Hand-written static HTML with one shared stylesheet and a few lines of progressive-enhancement JavaScript (a copy button on code blocks; every page renders fully with scripting off). No frameworks, no external fonts or other CDNs, no analytics or tracking of any kind; every page renders fully offline. Served from the repository's site/ directory via GitHub Pages from a workflow in .github/workflows/pages.yml (relative links throughout, so it works from the Pages subpath and from a local directory alike). Pages: Home, Why, Quickstart, Backends, Standards, Evidence, Explorer, Comparison, Roadmap, About. Figures: the cross-fidelity comparison SVG and the white-paper PDF, both regenerated and registered from run records by repository tooling.
