Trust dashboard

Adoption, tracked in the open

The project asks others to depend on it, so the same evidence discipline turns inward: the leading indicators of adoption live on one page, generated — never asserted, never softened. When the numbers are zero, that is what the page shows, because that is what the sources say; when a number cannot be measured yet, it reads UNKNOWN with its reason, because unknown is not zero.

The rules behind the numbers

What is being counted

What counts as a stranger

Anyone who is not a repository author identity and not automation: a login ending in [bot] is machinery, not a person depending on the tool, and a deleted account (no login) is still a stranger. The author list is the same one the reproduction gate enforces — one definition of "our own hands" everywhere.

Attempts count regardless of outcome

A reproduction attempt is a row whether it reproduced byte-for-byte, diverged (it enters the minimize-then-classify path), or stopped early (friction data). A comparison submission counts whether it was published or rejected — refusals are as visible as acceptances. Nothing is filtered for presentation.

A failed read is never a zero

If a public API cannot be read, the refresh job fails loudly and this page keeps its last committed values with their dates. A number appears only when a source was actually read — silence can never soften into a rounded-down zero.

No hand-curated numbers

Every value on this page is re-derived from committed records or fetched from a named API; the only human input the dashboard accepts is a pointer (which repository, which arXiv id), recorded in experiments/trust/sources.yaml. Editing the HTML by hand cannot stick: the next render overwrites it, and the suite fails on drift.

What is deliberately not here

Downloads, visits, star counts: this site runs no analytics and tracks nobody, so none of that is measured. The indicators are public acts — issues, pull requests, records, citations — visible to anyone, auditable against their sources by anyone.

How it updates

Two paths, no editor

  1. When a record lands. A reproduction record or a comparison submission committed to the tree re-derives its count locally; the suite fails until the page is re-rendered (make trust-dashboard), so the display cannot lag the evidence — the same freshness gate as the board and the community table.
  2. Weekly, from the APIs. A scheduled CI job runs tools/trust_dashboard.py --fetch (GitHub issues and pull requests; citations once sources.yaml names a public arXiv id) and commits the refreshed snapshot and page. The commit is machine-made and the job history is public — the page's age is visible, not hidden.

Why a page like this at all: the project's own decision points — double down, hold, or narrow — are to be made on evidence about adoption, and evidence here means numbers with sources. An indicator that stays at zero for a quarter is a finding, and this page is built so that finding is impossible to miss or to massage.
